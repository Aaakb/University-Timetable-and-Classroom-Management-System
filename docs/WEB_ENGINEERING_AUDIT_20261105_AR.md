# الفحص الهندسي لنسخة الويب — 5 نوفمبر 2026

تحديث: عولجت نتائج الويب لاحقاً في [تقرير الإصلاح](WEB_ENGINEERING_FIXES_20261105_AR.md). تبقى هذه الصفحة سجل نتائج الفحص قبل الإصلاح.

## الحكم
النسخة تعمل وظيفياً في المسارات المختبرة، لكنها لا تجتاز الاعتماد النهائي: توجد مشكلة مؤكدة في انتقال الواجهة بعد الحفظ السريع، والتسجيل المفتوح يمنح كل حساب وصولاً إدارياً. يلزم إغلاق النتائج العالية قبل اعتماد النسخة للتوزيع أو النشر العام. هذا فحص للكود والحزمة والاختبارات المتاحة، وليس إثباتاً لخلو جميع المسارات من العيوب.

## النطاق والمنهج
- مراجعة ASP.NET Core: التهيئة، المصادقة، التفويض، CSRF، الموارد، الاستيراد، التوليد، نسخ الجدول، التفضيلات، إدارة الأخطاء.
- مراجعة JavaScript وService Worker والقوالب وملفات CSS ومسار التنصيب والتشغيل المحلي.
- استخدام خريطة Graphify الموجودة لتحديد العلاقات ثم الرجوع إلى الكود الفعلي.
- اختبارات SQL ديناميكية على قواعد جديدة بأسماء فريدة مع حذفها بواسطة أدوات الاختبار؛ لم تستهدف الاختبارات تعديل قاعدة الجامعة.
- تشغيل Edge عبر Playwright، واختبارات أعطال الواجهة باستجابات API محاكاة؛ تمييزها عن اختبارات API الحقيقية أدناه.
- مقارنة جميع ملفات wwwroot الحالية مع ملفات حزمة WebInstaller-current: لا اختلافات.

## النتائج المرتبة

### 1. عالية P1 — اختفاء صفحة البيانات بعد الإضافة السريعة
الموضع: UniversityTimetable.API/wwwroot/js/app.js، الدالة navigate، الأسطر 101–124، ومسار الحفظ عند السطر 409.
تُخفى management عند الانتقال، ويتوقف إظهارها على تطابق state.epoch مع navigationEpoch بعد انتظار حركة التغطية. في المقابل يُتاح زر الإضافة بعد انتهاء load وقبل انتهاء الحركة. إذا حفظ المستخدم بسرعة، تستدعي عملية الحفظ load مرة ثانية، فتزيد epoch ويُلغى شرط إظهار management. النتيجة: الحفظ ينجح وتبقى الصفحة مخفية بلا رسالة خطأ.
الدليل: اختبار WebActualApi حفظ فرعاً ثم فشل عند النقر على زر تعديل غير ظاهر؛ وأُعيد إنتاج السبب باختبار Edge مستقل على API محاكاة: بعد الانتقال ثم الإضافة والحفظ مباشرة كانت managementHidden=true، وloadingHidden=true، ورسالة الخطأ فارغة. تجربة تحديث الصفحة أثناء الانتقال لم تُنتج المشكلة، لأن زر التحديث يعيد navigate إذا كانت الأقسام مخفية.
الإجراء: تعطيل الإضافة حتى اكتمال التنقل، وفصل هوية التنقل عن عدّاد تحميل البيانات، وضمان إعادة إظهار القسم بعد إعادة التحميل الناجحة. إضافة اختبار حفظ سريع أثناء الحركة.

### 2. عالية P1 للنشر المشترك — التسجيل المفتوح يتيح إدارة البيانات
الموضع: Controllers/AuthController.cs:46–52؛ Controllers/ResourcesController.cs:7؛ Controllers/SchedulingController.cs:12.
Register متاح دون تسجيل دخول، ولا توجد أدوار أو سياسات تفويض للتعديل والحذف والتوليد؛ Authorize يتحقق من تسجيل الدخول فقط. يستطيع حساب ينشئه أي شخص الوصول لوظائف إدارة البيانات. تأكد ذلك من اختبار التسجيل ثم تعديل المادة واستيراد بيانات بحساب جديد.
في الحزمة المحلية الربط بـ127.0.0.1 يقلل التعرض الشبكي، لكنه لا يجعل الحساب الجديد للقراءة فقط. تزداد الخطورة عند الاستضافة العامة أو مشاركة الوصول.
الإجراء: إيقاف التسجيل العام افتراضياً في النسخة ذات البيانات، وإنشاء الحسابات بواسطة مسؤول، وإضافة سياسات صريحة للقراءة والإدارة. الحد الأدنى الحالي لكلمة المرور أربعة أحرف في AuthService.cs:13، وهو بحاجة إلى سياسة أقوى إذا استُخدمت الحسابات عبر الشبكة.

### 3. متوسطة P2 — تقسيم الصفحات يجري بعد جلب كامل البيانات
الموضع: Controllers/ResourcesController.cs:17–19؛ ResourceCatalog.cs:30؛ wwwroot/js/api.js، الدالة all.
كل طلب صفحة يحمّل القائمة كاملة من SQL ثم يبحث ويقسمها في ذاكرة الخادم. الواجهة تطلب جميع الصفحات لتجمع القائمة كاملة. عند كبر البيانات يُعاد تحميل القائمة كاملة مرة لكل صفحة؛ وعدد الاستعلامات وحجم العمل يزدادان بلا حاجة.
الإجراء: نقل البحث والترتيب وSkip/Take وCount إلى IQueryable في قاعدة البيانات، وتحميل صفحة العرض فقط؛ توفير مسار خفيف مستقل لخيارات القوائم. لم يُنفذ اختبار حمل رقمي، لذا هذه نتيجة بنيوية وليست قياس زمن استجابة.

### 4. متوسطة P2 — مصير الخادم مرتبط بنافذة PowerShell بصورة غير موثوقة
الموضع: installer/Start-Web-Local.ps1:4، 10–23.
يُشغَّل الخادم كعملية مخفية منفصلة، ويعتمد إيقافه على finally بعد WaitForExit. إغلاق النافذة أو إنهاء عملية المشغّل قسرياً لا يضمن تنفيذ finally؛ قد يبقى الخادم على المنفذ 5187. عند التشغيل التالي يُرفض التشغيل لأي مستمع على المنفذ، دون التحقق من أنه نسخة التطبيق الموجودة أو توفير أمر إيقاف لها.
هذه نتيجة مراجعة دورة الحياة؛ لم يُنفذ اختبار إغلاق نافذة Windows بالقوة.
الإجراء: استخدام مشغّل يدير العملية بعلاقة حياة مضمونة مثل Windows Job Object، أو خدمة مُدارة مع أمر إيقاف واضح، والتعرف الآمن على نسخة التطبيق الموجودة قبل إعادة استخدام عنوانها.

### 5. متوسطة P2 — مجموعة اختبارات نقل البيانات لم تعد تطابق الواجهة الحالية
الموضع: tests/WebDataTransfer/Program.cs:100 وما بعدها؛ Controllers/ImportsController.cs:97؛ README.md ودليل WEB_PARITY_AR.md.
الاختبار يتوقع دعم استيراد Timetable بالوضع 2 وتوليده عبر imports/generate، لكن المتحكم يقبل AcademicData فقط، والواجهة تعرض استيراد التدريسيين والمواد. توقف الاختبار عند imports/validate المتوقّع 200. هذا يثبت اختلاف العقد بين الاختبار والتنفيذ؛ لا يثبت أن الاستيراد الأكاديمي معطل، فقد نجح اختباره الحقيقي.
README ما زال يصف دعم استيراد Excel/PDF بصورة أوسع من المتحكم الحالي الذي يقبل xlsx فقط. يلزم حسم نطاق المنتج وتحديث التوثيق والاختبارات، أو إعادة الوظائف إذا كانت مطلوبة.

### 6. متوسطة P2 — سجل الخطأ لا يحتفظ بما يكفي لتشخيص أخطاء الخادم
الموضع: ApiInfrastructure.cs:36–37.
يُسجل نوع الاستثناء والحالة ومعرف التتبع فقط، دون stack trace أو سبب الاستثناء حتى للأخطاء الداخلية 500. رسالة المستخدم تطلب الرجوع للسجل بواسطة رقم التتبع، لكن السجل لا يكفي غالباً لتحديد موقع العطل.
الإجراء: تسجيل تفاصيل تقنية منقحة وآمنة للأخطاء الداخلية في سجل محمي، دون قيم المدخلات أو بيانات الاتصال، مع الحفاظ على الرسالة العامة للمستخدم.

## نتائج الاختبارات الفعلية
- WebParity (.NET): ناجح؛ تدوير إعداد دمج العملي والحفاظ عليه عند غياب الحقل وقبول تغييره الصريح.
- WebActualApi: نجح بدء الخادم، التسجيل والدخول، قراءة الدمج وتعديل المادة، رفع Excel ومعاينته وحفظ أسماء التدريسيين والمواد. نجح دخول المتصفح ولوحة الإحصاءات وإضافة فرع؛ فشل التكامل عند زر التعديل غير الظاهر. لا تُحسب بقية خطوات هذا الاختبار ناجحة لأنها لم تنفذ.
- WebDataTransfer: نجحت حماية الاستعادة من البيانات المتغيرة، تعديل تفضيلات الأيام، حفظها مع تحسين الجدول، رفض المراجعة القديمة، حذف التفضيلات، استعادة الفصلين والتثبيت، ملكية رابط نسخة الأمان، التراجع بالنسخة الآمنة ورفض إعادة استخدام المعاينة. فشل عند عقد استيراد Timetable القديم؛ لم تنفذ خطوات التوليد التالية.
- WebParity/browser.mjs: نجحت الحالات الثلاث عشرة، بما فيها إبطال معاينة الاستيراد بعد تغيير الملف، رفض البيانات القديمة بعد فشل تحميل التفضيلات، مسح البيانات الخاصة عند انتهاء الجلسة، وتعطيل إجراءات الجداول البديلة عند الفشل، وعدم ظهور أخطاء JavaScript غير معالجة. هذه اختبارات API محاكاة.
- NuGet: dotnet list package --vulnerable --include-transitive لم يُبلغ عن حزم ضعيفة ضمن المصادر المتاحة وقت الفحص؛ هذه ليست مراجعة شاملة للمكتبات الأصلية أو كل الشيفرة.
- الحزمة: ملفات واجهة wwwroot مطابقة للمصدر الحالي؛ لم يُعد بناء Setup أو تعديله أثناء هذا الفحص.

## نقاط جيدة
تطبيق CSRF على طلبات التغيير، Cookies من نوع HttpOnly وSameSite، رفض HTTP للوصول الشبكي إلى API، منع تخزين API في Service Worker، قيود أحجام ملفات الاستيراد وفحص الحجم بعد فك الضغط، التحقق من ملكية المعاينات وروابط النسخ الآمنة، ومراجعات If-Match لتفادي الكتابة على نسخة قديمة. هذه ضوابط موجودة في الكود وليست شهادة باكتمال الأمان.

## حدود الفحص والمتابعة
لم يُختبر Setup على جهاز Windows نظيف أو بحساب مستخدم مختلف، ولم يُنفذ اختبار حمل أو تدقيق WCAG شامل أو اختبار توليد كامل على نسخة البيانات الحالية أو تحليل بصري شامل لملفات PDF. يلزم اختبار ترقية وإعادة تثبيت وإزالة البرنامج وفقد SQL وتعطل العملية أثناء الحفظ، وقياس الأداء على حجم بيانات ممثل قبل الاعتماد النهائي.
رُفض تلقائياً أمر إضافي لإنشاء خادم مستقل من لقطة الحزمة عبر سياسة تنفيذ الأدوات، دون سبب تفصيلي ظاهر؛ استُكمل التحقق من مشكلة الواجهة بخادم ملفات مؤقت وAPI محاكاة، مع بقاء اختبارات SQL الحقيقية المذكورة أعلاه منفذة بواسطة أدوات المشروع.
لم تُجر تعديلات إصلاحية على كود المنتج ولم تُغيّر الحزمة الموزعة. أولوية العمل: إصلاح النتيجتين 1 و2، ثم مزامنة عقد الاختبارات والتوثيق، ثم دورة حياة المشغّل وأداء الاستعلامات والتشخيص.
